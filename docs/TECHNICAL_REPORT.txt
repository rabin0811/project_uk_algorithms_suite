6. MODULE 1: INVENTORY MANAGEMENT SYSTEM
================================================================================

6.1 PROBLEM ANALYSIS

  Problem: A university department needs to track inventory items
  (equipment, stationery, furniture) with the ability to add, edit,
  delete, search, and sort items. The system must alert when stock
  is low and generate summary reports.

  Requirements:
    - Store item name, category, quantity, price, minimum stock level
    - Search by name or description
    - Sort by multiple attributes
    - Identify low-stock items automatically
    - Generate category-based reports

  Algorithm Selection:
    - Linear Search: Best for substring matching on text fields.
      Simple to implement and understand. O(n) is acceptable for
      moderate-sized inventories.
    - Binary Search: Used for exact name lookups when data is sorted.
      O(log n) provides significant speedup over linear search.
    - Merge Sort: Stable O(n log n) sort. Preserves relative order
      of equal elements. Good for name and price sorting.
    - Quick Sort: In-place O(n log n) average. Fast for quantity
      sorting. Lower constant factor than Merge Sort.

  Data Structure Selection:
    - List: Sequential storage of InventoryItem objects. Maintains
      insertion order and allows indexing.
    - Dictionary: Hash-based indices for O(1) lookups by ID, name,
      and category. Enables fast access without linear scanning.

6.2 ALGORITHM DESIGN & PSEUDOCODE

  --- Linear Search (substring matching) ---
  FUNCTION LinearSearchText(items, searchTerm):
    results = []
    FOR EACH item IN items:
      IF searchTerm IN item.name (case-insensitive)
         OR searchTerm IN item.description (case-insensitive):
        ADD item TO results
    RETURN results

  --- Binary Search (exact name) ---
  FUNCTION BinarySearch(items, targetName):
    low = 0, high = len(items) - 1
    target = targetName.lower()
    WHILE low <= high:
      mid = (low + high) // 2
      midName = items[mid].name.lower()
      IF midName == target: RETURN items[mid]
      ELSE IF midName < target: low = mid + 1
      ELSE: high = mid - 1
    RETURN None

  --- Merge Sort ---
  FUNCTION MergeSort(items, key):
    IF len(items) <= 1: RETURN items
    mid = len(items) // 2
    left = MergeSort(items[:mid], key)
    right = MergeSort(items[mid:], key)
    RETURN Merge(left, right, key)

  FUNCTION Merge(left, right, key):
    result = []
    WHILE left NOT EMPTY AND right NOT EMPTY:
      IF left[0].key <= right[0].key:
        APPEND left[0] TO result; REMOVE left[0]
      ELSE:
        APPEND right[0] TO result; REMOVE right[0]
    APPEND remaining left TO result
    APPEND remaining right TO result
    RETURN result

6.3 DRY RUN

  Input: items = [{name:"Delta"}, {name:"Alpha"}, {name:"Beta"}, {name:"Gamma"}]
  Sort by: name (ascending)

  MergeSort([D, A, B, G], "name"):
    mid = 2
    left  = MergeSort([D, A], "name"):
      mid = 1
      left  = MergeSort([D], "name") -> [D]
      right = MergeSort([A], "name") -> [A]
      Merge([D], [A]): "A" < "D" -> [A, D]
    right = MergeSort([B, G], "name"):
      -> [B, G]
    Merge([A, D], [B, G]):
      A < B -> [A]
      D > B -> [A, B]
      D < G -> [A, B, D]
      -> [A, B, D, G]

  Result: [Alpha, Beta, Delta, Gamma] -- correct alphabetical order.

6.4 COMPLEXITY ANALYSIS

  Algorithm          | Time Complexity    | Space Complexity    | Stability
  -------------------|-------------------|---------------------|----------
  Linear Search      | O(n)              | O(1) auxiliary      | N/A
  Binary Search      | O(log n)          | O(1) auxiliary      | N/A
  Merge Sort         | O(n log n)        | O(n) auxiliary      | Stable
  Quick Sort         | O(n log n) avg    | O(log n) (stack)    | Unstable
                     | O(n^2) worst      |                     |

  - Linear Search uses O(1) extra space (only loop variable and result
    list, which is O(k) for k results).
  - Binary Search uses O(1) extra space (low, high, mid pointers).
  - Merge Sort requires O(n) auxiliary array for merging.
  - Quick Sort requires O(log n) stack space for recursion (worst
    case O(n) for unbalanced partitions).

7. MODULE 2: SHARED RESOURCE SCHEDULING SYSTEM
================================================================================

7.1 PROBLEM ANALYSIS

  Problem: Multiple users need to book shared resources (meeting rooms,
  equipment). The system must prevent double-booking by detecting
  time interval overlaps.

  Requirements:
    - CRUD operations on bookings
    - Automatic conflict detection when creating/editing bookings
    - Daily schedule viewing
    - Available time slot finding
    - Booking history

  Algorithm Selection:
    - Interval Overlap Detection: Core algorithm for conflict detection.
      Two intervals [s1, e1) and [s2, e2) overlap if s1 < e2 AND s2 < e1.
    - Sweep Line: For detecting ALL overlaps in a collection, sort all
      start/end events and sweep through with an active set.
    - Binary Search: Find bookings by resource name efficiently.
    - Merge Sort: Sort bookings by time for schedule display.

  Data Structure Selection:
    - List: Stores Booking objects in sequence.
    - Interval: Each booking represents a [start, end) time interval.
      The Booking model has start_datetime/end_datetime properties
      and an overlaps_with() method.

7.2 ALGORITHM DESIGN & PSEUDOCODE

  --- Interval Overlap Detection (single pair) ---
  FUNCTION Overlaps(booking1, booking2):
    IF booking1.resource != booking2.resource:
      RETURN False
    RETURN booking1.start < booking2.end
           AND booking2.start < booking1.end

  --- Sweep Line (detect all conflicts) ---
  FUNCTION DetectAllOverlaps(bookings):
    events = []
    FOR EACH booking IN bookings:
      ADD (booking.start, "start", booking) TO events
      ADD (booking.end, "end", booking) TO events
    SORT events by time (end before start at same time)
    active = []
    FOR EACH (time, type, booking) IN events:
      IF type == "start":
        FOR EACH activeBooking IN active:
          IF activeBooking.resource == booking.resource:
            ADD (activeBooking, booking) TO conflicts
        ADD booking TO active
      ELSE:
        REMOVE booking FROM active
    RETURN conflicts

7.3 DRY RUN

  Input bookings:
    B1: Room A, 09:00-10:00
    B2: Room A, 09:30-10:30
    B3: Room B, 10:00-11:00

  Events (sorted):
    09:00 start B1  -> active = [B1]
    09:30 start B2  -> Check B1(resource match): CONFLICT! active = [B1, B2]
    10:00 end   B1  -> active = [B2]
    10:00 start B3  -> Check B2(resource mismatch): OK. active = [B2, B3]
    10:30 end   B2  -> active = [B3]
    11:00 end   B3  -> active = []

  Conflicts found: [(B1, B2)] -- correct.

7.4 COMPLEXITY ANALYSIS

  Algorithm              | Time Complexity    | Space Complexity
  -----------------------|-------------------|------------------
  Single Overlap Check   | O(1)              | O(1)
  Sweep Line (all)       | O(n log n)        | O(n)
  Binary Search          | O(log n)          | O(1)
  Available Slots        | O(n log n)        | O(n)
  Sort by Time           | O(n log n)        | O(n)

  The sweep line algorithm sorts 2n events (O(2n log 2n) = O(n log n))
  and processes each event in O(1) average time. The active set stores
  at most n intervals at once, requiring O(n) space.

8. MODULE 3: DYNAMIC RESOURCE ALLOCATION SYSTEM
================================================================================

8.1 PROBLEM ANALYSIS

  Problem: An operating system needs to allocate CPU time to multiple
  processes. Different scheduling strategies affect waiting time,
  turnaround time, and overall system efficiency.

  Requirements:
    - Add/remove processes with burst time, priority, arrival time
    - Implement 4 scheduling algorithms
    - Display execution order, waiting time, turnaround time
    - Visualize the waiting queue
    - Track process history

  Algorithm Selection:
    - FCFS (First Come First Served): Simplest algorithm. Processes
      execute in arrival order. Non-preemptive.
    - SJF (Shortest Job First): Minimizes average waiting time by
      selecting shortest burst first. Non-preemptive.
    - Round Robin: Fair time-sharing with a fixed time quantum.
      Preemptive -- each process gets the quantum in cyclic order.
    - Priority Scheduling: Higher priority (lower number) executes
      first. Implemented with MinHeap for O(log n) selection.

  Data Structure Selection:
    - Queue (list as FIFO): Used for FCFS and Round Robin ready queue.
    - MinHeap: Used for Priority Scheduling. Provides O(log n) insert
      and extract-min operations.
    - PriorityQueue: Wrapper around MinHeap for (priority, item) pairs.

8.2 ALGORITHM DESIGN & PSEUDOCODE

  --- FCFS ---
  FUNCTION FCFS(processes):
    sort processes by arrival_time
    currentTime = 0
    FOR EACH process:
      IF currentTime < process.arrivalTime:
        currentTime = process.arrivalTime
      process.startTime = currentTime
      process.waitingTime = currentTime - process.arrivalTime
      currentTime += process.burstTime
      process.turnaroundTime = currentTime - process.arrivalTime
      process.status = "completed"
    RETURN schedule with metrics

  --- Round Robin ---
  FUNCTION RoundRobin(processes, quantum):
    queue = processes sorted by arrival
    WHILE processes NOT all completed:
      process = queue.dequeue()
      executeTime = min(quantum, process.remainingTime)
      currentTime += executeTime
      process.remainingTime -= executeTime
      IF process.remainingTime == 0: mark completed
      ELSE: queue.enqueue(process)
    RETURN schedule with metrics

  --- MinHeap-based Priority ---
  FUNCTION PriorityScheduling(processes):
    sortedByArrival = sort(processes, by arrivalTime)
    minHeap = PriorityQueue()     // smaller key = higher priority
    currentTime = 0, idx = 0
    WHILE idx < n OR heap NOT empty:
      // Add all processes that have arrived
      WHILE idx < n AND sortedByArrival[idx].arrivalTime <= currentTime:
        heap.enqueue(priority, process)
        idx++
      IF heap.empty: advance to next arrival
      process = heap.dequeue()   // O(log n)
      process.completionTime = currentTime + process.burstTime
      currentProcess.execute()
    RETURN schedule with metrics

8.3 DRY RUN

  Input: P1(bt=6, prio=3, arr=0), P2(bt=8, prio=2, arr=1),
         P3(bt=4, prio=1, arr=2), P4(bt=10, prio=4, arr=3)

  FCFS Execution:
    Time 0: P1 arrives -> execute P1 (0 to 6)
    Time 1: P2 arrives (waits)
    Time 2: P3 arrives (waits)
    Time 3: P4 arrives (waits)
    Time 6: P1 done -> execute P2 (6 to 14)
    Time 14: P2 done -> execute P3 (14 to 18)
    Time 18: P3 done -> execute P4 (18 to 28)

    Waiting times: P1=0, P2=5, P3=12, P4=15
    Avg Waiting: (0+5+12+15)/4 = 8.00
    Avg Turnaround: (6+13+16+25)/4 = 15.00

  Priority Scheduling (MinHeap):
    Time 0: P1 arrives (prio=3). Heap = [P1]
    Time 0: Dequeue P1 -> execute (0 to 6)
    Time 1: P2 arrives (prio=2). Heap = [P2]
    Time 2: P3 arrives (prio=1). Heap = [P2, P3]
    Time 3: P4 arrives (prio=4). Heap = [P2, P3, P4]
    Time 6: P1 done. Dequeue P3 (highest prio=1) -> execute (6 to 10)
    Time 10: P3 done. Dequeue P2 (prio=2) -> execute (10 to 18)
    Time 18: P2 done. Dequeue P4 (prio=4) -> execute (18 to 28)

    Waiting times: P1=0, P2=9, P3=4, P4=15
    Avg Waiting: (0+9+4+15)/4 = 7.00

8.4 COMPLEXITY ANALYSIS

  Algorithm        | Time Complexity    | Space Complexity    | Preemptive
  -----------------|-------------------|---------------------|-----------
  FCFS             | O(n log n)        | O(n)                | No
  SJF              | O(n^2)            | O(n)                | No
  Round Robin      | O(n * cycles)     | O(n)                | Yes
  Priority (heap)  | O(n log n)        | O(n)                | No

  - FCFS: O(n log n) for sorting by arrival, O(n) for execution.
  - SJF: O(n^2) because at each step we scan remaining processes
    to find the shortest available burst.
  - Round Robin: Each process may be scheduled multiple times.
    Total operations depend on burst times and quantum.
  - Priority with MinHeap: O(n log n) since each of n processes
    is inserted once and extracted once (each O(log n)).

10. PROBLEMS FACED DURING DEVELOPMENT
================================================================================

PROBLEM 1: Parameter Name Mismatch
  - Issue: The sample data generator used "min_stock_level" as the
    dictionary key, but the InventoryController.add_item() method
    expected "min_stock" as the parameter name. This caused a
    TypeError when using **kwargs unpacking.
  - Impact: Sample data could not be loaded on first run.
  - Resolution: Renamed the controller parameter from "min_stock"
    to "min_stock_level" to match the database column name, model
    property name, and sample data key. This ensured consistency
    across the entire data flow.

PROBLEM 2: Inline __import__ Usage
  - Issue: The interval.py find_available_slots() function used
    __import__("datetime").timedelta instead of importing timedelta
    at the top of the file. This was poor practice, made the code
    harder to read, and had minor performance overhead.
  - Impact: Code maintainability issue; would not pass code review.
  - Resolution: Replaced all __import__ calls with a proper
    "from datetime import timedelta" import at the module level.

PROBLEM 3: Dashboard Buttons Non-Functional
  - Issue: The Dashboard view's "Quick Actions" buttons were created
    without command callbacks, making them decorative only. Users
    could not navigate from the dashboard.
  - Impact: Poor UX; broken workflow.
  - Resolution: Added a nav_callback parameter to DashboardView.
    The App class now passes self._show_view as the callback.
    Each button's command lambda calls the callback with the
    appropriate view ID.

PROBLEM 4: Midnight Boundary in Tests
  - Issue: Several scheduling tests used datetime.now() to create
    bookings. When tests ran near midnight, adding timedelta(hours=1)
    or timedelta(hours=2) would cross the day boundary, causing
    get_bookings_for_date() to return fewer bookings than expected.
  - Impact: Intermittent test failures depending on time of day.
  - Resolution: Fixed all test dates to use explicit datetime
    objects (e.g., datetime(2026, 7, 22, 10, 0, 0)) rather than
    datetime.now(). This made tests deterministic and independent
    of execution time.

PROBLEM 5: Low Stock Test Data Inconsistency
  - Issue: The test_inventory.py TestInventoryCollection.setUp()
    created a Laptop item with quantity=5 and min_stock_level=2.
    The test expected this to be low stock, but 5 > 2 means it
    was NOT low stock, causing a test failure.
  - Impact: False test failure.
  - Resolution: Changed min_stock_level to 10 for the Laptop,
    making quantity=5 < 10 = low stock. Then verified the fix
    with the correct assertion.

14. FUTURE RECOMMENDATIONS
================================================================================

1. ADD PREEMPTIVE PRIORITY SCHEDULING:
   Currently, Priority Scheduling is non-preemptive. Adding preemptive
   priority scheduling would allow higher-priority processes to
   interrupt lower-priority ones mid-execution.

2. IMPLEMENT MULTI-LEVEL QUEUE SCHEDULING:
   Combine Round Robin (foreground/interactive processes) with FCFS
   (background/batch processes) in a two-level queue system.

3. ADD DATA VISUALIZATION:
   Currently, results are displayed as text. Adding matplotlib-based
   Gantt charts for scheduling and bar charts for inventory would
   significantly improve analysis capabilities.

4. EXPORT FUNCTIONALITY:
   Add PDF/CSV export for inventory reports, booking schedules, and
   algorithm results. This would help students include output in
   their technical reports.

5. ADVANCED SEARCH:
   Implement more sophisticated search algorithms:
   - Interpolation Search for uniformly distributed numeric data
   - Ternary Search for unimodal functions
   - Rabin-Karp for string pattern matching

6. REAL-TIME NOTIFICATIONS:
   Add desktop notifications for low-stock alerts and scheduling
   conflicts using system notification APIs.

7. MULTI-USER SUPPORT:
   Add user authentication and role-based access control. Different
   users could have different permissions (admin, staff, viewer).

8. THEME CUSTOMIZATION:
   Allow users to switch between dark/light mode and customize
   accent colors through a settings panel.

9. CLOUD SYNCHRONISATION:
   Optional sync with cloud storage for cross-device access to
   inventory and scheduling data.

10. PERFORMANCE OPTIMISATION:
    For very large datasets (100K+ items), consider:

    - Balanced BST (AVL/Red-Black) for O(log n) operations
    - B-Trees for database indexing
    - External sorting for datasets that don't fit in memory
    - Multi-threading for parallel algorithm execution

  "The algorithm implementations are correct and well-optimized. The
